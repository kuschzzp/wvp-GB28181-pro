# 06 GB28181 设备接入

[上一章：首次部署](05-first-deployment.md) · [返回首页](README.md) · [下一章：域名、HTTPS 与 NAT](07-domain-https-and-nat.md)

本章使用一台设备完成最小闭环。大华、水星以及其他品牌、型号、固件的菜单名称差异很大，因此这里只给字段含义和验证方法，不编造某个型号的点击路径。

目标分为三个阶段：

1. 设备注册在线；
2. 平台收到设备目录和通道；
3. 点击点播后，设备把 RTP 发到 ZLMediaKit，浏览器能播放。

三个阶段必须逐个通过。设备显示“注册成功”不等于平台已经收到通道，更不等于视频链路正常。

当前项目的受保护播放票据会优先使用 ZLMediaKit 上报的 `HTTPS:443`。如果你还只开放了章节 05 的 HTTP `8080` 管理入口，可以先在本章确认 INVITE、RTP 和流注册成功，再完成 [07 域名、HTTPS 与 NAT](07-domain-https-and-nat.md) 后验收浏览器画面；不要把 TLS 入口缺失和设备未发流混成同一个故障。

## 1. 接入前收集设备信息

为每台设备建立记录：

| 项目 | 示例/说明 | 你的实际值 |
|---|---|---|
| 品牌、型号、固件版本 | 大华/水星具体型号 |  |
| 设备管理地址 | 例如 `192.168.10.51` |  |
| 设备网关和 DNS | 跨网段/NAT 时必须正确 |  |
| 设备时间和时区 | 应与平台接近 |  |
| 是否支持 GB/T 28181 | 查看设备说明或页面 |  |
| 设备 20 位国标 ID | 每台唯一 |  |
| 视频通道国标 ID | 每通道唯一 |  |
| 本地 SIP 端口 | 设备自身监听端口，不等于平台 8160 |  |
| SIP 传输 | UDP 或 TCP |  |
| 媒体传输模式 | UDP、TCP 被动或 TCP 主动 |  |
| 主/子码流编码 | 首测推荐 H.264 |  |
| 实际码率 | 用于带宽和录像估算 |  |

设备时间明显错误时，摘要认证、日志对齐、录像检索和问题复现都会变困难。先设置 NTP、Asia/Shanghai 或设备支持的正确时区。

## 2. 平台参数与设备字段对照

不同厂商可能使用括号中的名称：

| 平台值 | 设备常见字段名 | 填写规则 |
|---|---|---|
| `SIP_ShowIP` 对应的可达地址 | SIP 服务器、平台地址、服务器 IP | 从设备网络访问平台的地址，不能填 `127.0.0.1` |
| `SIP_Port` | 服务器端口、平台注册端口 | 当前默认 `8160` |
| `SIP_Id` | 服务器 ID、平台编码、SIP 服务器编号 | 平台 20 位 ID |
| `SIP_Domain` | 域、Realm、服务器域 | 当前平台规划的 10 位域 |
| `SIP_Password` | 认证密码、注册密码 | 与平台一致，注意大小写 |
| 设备自己的 ID | 设备 ID、SIP 用户名、设备编码 | 每台设备唯一的 20 位编码 |
| 通道自己的 ID | 视频通道编码、报警通道编码 | 每个通道唯一，不要全部等于设备 ID |
| UDP/TCP | 传输协议、注册协议 | 设备和网络策略一致 |
| 注册有效期 | Expires、注册周期 | 使用设备支持的合理值，配合保活 |
| 心跳周期/超时次数 | Keepalive、心跳间隔 | 保持 NAT 映射并及时判断离线 |

### 2.1 最常见的 ID 混淆

- 平台 ID：WVP 自己的 20 位 `SIP_Id`；
- 设备 ID：每台摄像机/NVR/编码器自己的 20 位编号；
- 通道 ID：设备下每个视频通道的 20 位编号；
- 域：通常是 10 位 `SIP_Domain`，不是域名网址。

设备页面中的“用户名”有时要求设备 ID，有时是单独认证用户名。优先看厂商对 GB28181 字段的说明；如果页面只有一个“设备 ID/用户名”，一般应与设备国标 ID 保持一致，但要用实际 REGISTER 报文确认。

### 2.2 编码唯一性

同一平台中设备 ID 和通道 ID必须唯一。复制一台设备配置到另一台时，如果忘记改国标 ID，平台可能反复上下线、覆盖状态或把目录归到错误对象。

先用表格集中分配编码，再配置设备，不要让现场人员随意填写“看起来是 20 位”的数字。

## 3. 大华和水星设备的配置原则

厂商页面可能位于“网络”“平台接入”“国标”“GB/T 28181”“接入协议”等栏目。固件升级后位置也可能改变。

通用操作顺序：

1. 登录设备管理页面并备份现有配置；
2. 校准网络、网关、DNS、时间和 NTP；
3. 启用 GB28181/国标接入；
4. 填平台地址、端口、平台 ID、域和密码；
5. 填设备 ID、本地 SIP 端口和传输协议；
6. 为要上报的视频通道分配唯一国标通道 ID并启用；
7. 选择首测码流，优先 H.264；
8. 保存并在设备要求时重启 GB 服务或设备；
9. 同时观察平台日志和网络包，不只看设备页面的一行状态。

不要因为“大华另一款型号是这个菜单”就强行套用。没有相同固件文档时，找字段，不猜菜单。

## 4. 传输协议如何选

### 4.1 SIP UDP

优点是兼容广、配置简单；缺点是网络丢包时没有传输层重传，跨 NAT 依赖心跳维持映射。

同一局域网首次接入通常可以从 UDP 开始。平台必须开放 `8160/udp`。

### 4.2 SIP TCP

需要设备主动连接平台 `8160/tcp`，跨复杂网络有时更稳定，但设备固件支持质量不同。切换 TCP 后必须同时检查安全组、路由器和防火墙 TCP 规则，不能只在设备上改协议。

### 4.3 RTP UDP

视频数据由设备连续发向平台 `10003/udp`。延迟较低，丢包时可能花屏或卡顿。公网环境要重点检查 MTU、丢包、带宽和 UDP 限制。

### 4.4 RTP TCP 主动/被动

“主动/被动”的命名要从设备视角还是平台视角判断，厂商界面可能相反。不要只凭中文标签猜；抓点播时的 TCP SYN 方向确认谁发起连接。

当前 WVP/ZLMediaKit 也发布 `10003/tcp`。修改设备媒体模式后，WVP 中对应设备的流传输模式也要一致。

## 5. 阶段一：验证注册

### 5.1 同时打开 WVP 日志

执行目录：Compose 目录。

```bash
cd /opt/wvp-GB28181-pro/docker
docker compose logs -f --tail=200 polaris-wvp
```

然后在设备页面保存 GB28181 配置或手动触发注册。观察与设备 ID、REGISTER、认证、上线相关的日志。不同版本日志文本可能不同，不要只依赖某一条固定文案。

按 `Ctrl+C` 退出日志跟踪。

### 5.2 抓 SIP 数据包

在另一个 SSH 窗口：

```bash
sudo tcpdump -ni any port 8160
```

预期流程通常包括：

1. 设备向平台发送 REGISTER；
2. 平台返回认证挑战；
3. 设备携带摘要认证再次 REGISTER；
4. 平台返回成功响应；
5. 设备周期性发送 Keepalive/MESSAGE 或重新注册。

如果服务器完全看不到 REGISTER：

- 设备平台地址/端口填错；
- 设备网关或路由不通；
- SIP TCP/UDP 协议不一致；
- 云安全组、Linux 防火墙或 NAT 没放行；
- 设备所在网络限制出站；
- 公网地址处于 CGNAT/双层 NAT 且映射不完整。

如果看得到 REGISTER 但反复认证：

- 平台 ID、域、设备 ID或密码不一致；
- 密码有不可见空格或设备不支持某些特殊字符；
- 设备时间异常；
- 两台设备使用相同 ID；
- 设备计算摘要时对 Realm/用户名的理解与填写不一致。

如果平台返回成功但很快离线：

- 心跳未发送或响应回不到设备；
- NAT 映射过早过期；
- 注册周期/心跳超时设置不合适；
- 设备网络抖动；
- WVP 容器在重启或 Redis/MySQL 不稳定。

### 5.3 页面验收

平台设备列表应出现准确设备 ID、来源 IP和在线状态。不要仅凭设备自己的“已注册”绿灯；平台和设备两边都要确认。

## 6. 阶段二：验证目录和通道

设备在线后，在 WVP 设备页面执行目录同步/刷新通道。同步时同时看 WVP 日志：

```bash
docker compose logs -f --tail=300 polaris-wvp
```

目录链路通常是平台发送 Catalog 查询，设备通过 SIP MESSAGE 分批返回通道 XML。

预期：

- 设备下出现正确数量的通道；
- 通道 ID唯一；
- 通道名称、在线状态与设备相符；
- NVR 多通道不会只出现设备本身一条；
- 再次同步不会生成大量重复通道。

### 6.1 设备在线但没有通道

按顺序检查：

1. WVP 是否真的发出了 Catalog；
2. Catalog 发往的设备地址、端口和协议是否可达；
3. 设备是否返回 MESSAGE；
4. 返回 XML 是否包含 DeviceList 和通道；
5. 设备页面是否为视频通道启用了国标上报；
6. 通道 ID 是否为空、重复或格式不被设备接受；
7. WVP 日志是否有 XML 解析或数据库约束错误。

“注册成功但没有通道”主要是信令/目录问题，还没进入 RTP 媒体阶段。此时反复开放 `10003` 不会解决 Catalog。

### 6.2 通道显示离线

设备本身在线不代表每个视频源都有信号。NVR 可能在线，但某路摄像机断网；设备也可能上报通道状态为 OFF。

检查设备本地预览、通道绑定、摄像机到 NVR 的状态，然后重新同步。不要在数据库里手工把状态改成在线，那只会掩盖真实状态。

## 7. 把设备绑定到视频资源组

目录同步成功后，进入“系统管理 → 视频资源组”：

1. 选择或创建一个资源组；
2. 绑定整台设备或指定通道；
3. 给业务角色设置“指定资源组”视频范围；
4. 确认角色具有点播、查看等必要功能权限；
5. 用普通用户重新登录验证。

部门不会自动决定设备归属。一个总部用户可以通过角色看到某园区视频组，也可以完全看不到同部门其他用户所管理的视频；这取决于角色的视频资源组授权。

授权整台设备适合“以后新增通道也随设备授权”的场景；只授权通道适合严格分路隔离。决定前先明确业务责任边界。

## 8. 阶段三：验证点播和 RTP

### 8.1 同时观察两类日志

窗口一：

```bash
docker compose logs -f --tail=300 polaris-wvp
```

窗口二：

```bash
docker compose logs -f --tail=300 polaris-media
```

然后在平台点击某个通道播放。

如果尚未按章节 07 配置 443 TLS 入口，点击后浏览器画面可能失败；此时本节仍可用日志和抓包验证设备是否已经发流。浏览器播放必须等媒体 URL、TLS 和 `/rtp/` 代理同时正确后才算通过。

WVP 侧关注：是否发送 INVITE、设备是否返回 200 OK、SDP 协商地址/端口、SSRC/流标识、是否等待流超时。

ZLMediaKit 侧关注：RTP 端口是否收到流、流是否注册、轨道是否就绪、Hook 是否成功、是否因鉴权或格式拒绝。

### 8.2 抓 RTP

```bash
sudo tcpdump -ni any port 10003
```

按当前 `.env` 端口替换。

判断：

- 完全没有 RTP：重点查 SDP_IP、NAT、端口、设备媒体模式、设备是否真正开始发送；
- 有少量握手/探测后停止：查 INVITE/ACK、设备超时和 TCP 主被动模式；
- 持续有 RTP，但 ZLMediaKit 没有流：查 TCP/UDP 模式、SSRC、负载类型、PS 封装、端口和 ZLM 日志；
- ZLMediaKit 已有流但浏览器失败：转查 Nginx `/rtp/`、播放票据、浏览器编码支持和 `Stream_IP`。

### 8.3 核对 SDP 中的地址

抓 SIP 全文时可临时使用：

```bash
sudo tcpdump -ni any -A port 8160
```

找到 INVITE 的 SDP，检查媒体连接地址是否是设备可达的 `SDP_IP`，端口是否是实际 `MediaRtp`。不要长期输出全文；它可能包含设备 ID和认证相关字段。

## 9. 有声音无画面、黑屏或卡顿

### 9.1 编码兼容

首次验证优先：

- 视频 H.264；
- 音频 G.711A/PCMA 或项目/浏览器明确支持的编码；
- 合理分辨率和码率；
- 先用子码流降低网络压力。

H.265 在浏览器端的支持受浏览器、系统和播放协议影响。ZLMediaKit 收到 H.265 不代表每个浏览器都能直接解码。先用 H.264 证明链路，再评估 H.265 播放方案。

### 9.2 关键帧和 GOP

浏览器可能需要等到关键帧才出画面。GOP 太长会导致首屏慢；设备没有按请求发送 I 帧时也可能长时间黑屏。检查设备编码页和 ZLM 轨道日志，不要把所有黑屏都归因于防火墙。

### 9.3 带宽、丢包和 MTU

公网 UDP 丢包会导致花屏、卡顿。使用 `tcpdump`、交换机/路由器统计和设备码率核对：

- 实际输入速率是否接近设备码率；
- 服务器网卡是否丢包；
- 云服务器入站/出站带宽是否限速；
- 多路同时播放是否导致总带宽超限；
- VPN/隧道是否因 MTU 造成分片问题。

## 10. 录像验证

如果 `RecordSip=true`，点播一段时间后检查宿主机录像目录：

```bash
cd /opt/wvp-GB28181-pro/docker
du -sh volumes/video
find volumes/video -type f -mmin -10 -print | head
```

有新文件不等于录像一定可恢复播放；还要在平台按权限查询、播放/下载一段，并确认普通用户只能访问其视频资源组范围内的录像。

若只是验证直播而未规划磁盘，保持 `RecordSip=false`，避免无意占满系统盘。

## 11. 推流、拉流和地址生成

GB28181 点播通常是按需过程：平台发送 INVITE，设备开始 RTP，WVP 返回受授权控制的播放信息。不要把 ZLMediaKit 的原始内部 URL 当作长期公开地址。

对于其他来源：

- RTSP 拉流在平台的拉流代理/拉流管理中配置来源 URL；
- RTMP 推流在推流管理中生成或登记入口；
- 这些资源也应加入视频资源组，并给角色分配对应功能和对象范围；
- API 对接使用短期播放/下载票据和受限 API Key，不要绕过 WVP 直接公开 ZLM HTTP 端口；
- 地址、端口和协议仍由 ZLMediaKit 实际承载，WVP 负责管理、授权和调度。

## 12. 批量设备接入方法

第一台完整通过后再批量：

1. 制作设备清单和唯一编码表；
2. 按现场/网段分批，每批少量设备；
3. 每批先看注册成功率；
4. 再批量同步目录并核对通道数；
5. 抽样主码流、子码流、音频、云台和录像；
6. 绑定视频资源组并用普通角色抽检；
7. 记录厂商、型号、固件的字段差异；
8. 出现共性故障时暂停下一批，先确认平台还是同固件问题。

不要一次把所有大华、水星设备都改完再排错。分批能让网络、固件和字段差异更容易定位。

## 13. 单设备验收表

- [ ] 设备时间、网关、DNS 正确；
- [ ] 平台地址、端口、域、平台 ID、设备 ID和密码已核对；
- [ ] 设备 ID与通道 ID唯一；
- [ ] WVP 收到 REGISTER 并显示设备在线；
- [ ] 心跳/重注册持续稳定；
- [ ] Catalog 返回通道数量正确；
- [ ] 通道在线状态与设备本地一致；
- [ ] 点播时 INVITE/200 OK/ACK 链路完整；
- [ ] 服务器 `10003` 收到持续 RTP；
- [ ] ZLMediaKit 识别音视频轨道；
- [ ] 浏览器能播放，首屏和延迟可接受；
- [ ] 普通用户只能看到授权视频资源组；
- [ ] 若启用录像，查询、播放和权限验证通过。
